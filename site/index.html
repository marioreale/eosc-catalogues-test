EOSC Federation Nodes Catalogues

This page reports the status and preliminary basic compliance tests outcome for the Nodes Catalogues (both Services and Research Products) that are contributed to the EOSC Exchange by the EOSC Production 1.0 Federation Nodes (excluding the EOSC EU Node [EEN] itself). These resources, in addition to the ones directly contributed by the EEN, are published by the EEN Resource Hub.

The test suite today only checks that each endpoint is configured correctly and answers in the right form. Every catalogue configured in catalogues.yaml, one card each, with the node that contributes it. Service Catalogues and Research Product Catalogues are reported separately. Scope of the test suite

What this test suite tests today

Configuration checks (offline)

These check the entry in catalogues.yaml, not the server:

  • all required fields are present;
  • the node is a known EOSC Node;
  • the protocol matches the catalogue type;
  • the endpoint uses HTTPS;
  • an OAI-PMH base URL has no ?verb= in it;
  • the endpoint comes from the production sheet, or the Resource Hub record is named.

One live request per catalogue (the probe)

Service catalogues: a single GET of the endpoint.

  • Green means HTTP 200 and a body that parses as JSON.
  • It also notes total, totalCount or count and the number of items on the first page, if it finds them.
  • It does not check field names or types, or that the API follows the EEN services API.

OAI-PMH (research products): a single ?verb=Identify.

  • Green means HTTP 200, valid XML, no OAI-PMH <error>, and an <Identify> element.
  • It reports repositoryName, protocolVersion, baseURL and earliestDatestamp.
  • It flags a declared baseURL that differs from the endpoint queried, but that does not turn the probe red.

What it does not test

AreaNot tested
OAI-PMH protocolThe other five verbs (ListMetadataFormats, ListSets, ListIdentifiers, ListRecords, GetRecord), resumption tokens, error codes for bad arguments, date ranges, XML schema validation of the responses
OpenAIRE guidelinesWhether oai_openaire or oai_datacite is offered, the required elements, and the vocabularies
EEN services APIThe response schema, required fields, paging, filtering, versioning
HarvestingReading the whole catalogue, record counts against declared totals, duplicates, deleted records
Metadata qualityValidation against DCAT or DCAT-AP (for example with SHACL), mandatory properties, licences, persistent identifiers

A green probe therefore shows the endpoint is online and speaks JSON or OAI-PMH. It does not show that the catalogue is compliant.

What each card shows

Configuration

The checks of the test suite, evaluated for this entry: required fields, known node, protocol matching the type, HTTPS endpoint, OAI-PMH base URL without ?verb=, endpoint taken from the production sheet and the Resource Hub record named. No network involved.

Availability probe

One request per endpoint during the run: GET the services endpoint (must answer 200 with JSON) or ?verb=Identify on the OAI-PMH base URL (must answer 200 with an Identify response).

Source

Endpoints come from the production sheet (production_env_node_services.xlsx, October 2026) and the EOSC EU Node Resource Hub.

Not tested: Full compliance with all the EEN services API or the OpenAIRE guidelines, harvesting of records, and metadata quality (DCAT/DCAT-AP). A green probe only means the endpoint is up and speaks the expected format.
